The Visual Execution Layer is BASIL's human-facing behavioural execution interface over canonical task state. It is not a separate source of truth and it does not replace BASIL's task register, source lineage or task-state rules.

Drive evidence establishes that this capability progressed beyond design. On 19 August 2026 a working deployment existed at `project-basil.davidbarske.chatgpt.site` and was subjected to a formal Phase 1 engineering review. That review documented concrete defects in the running build, including card collisions, static layouts, non-functional strategy/persona selectors, missing physical drop kinetics, weak temporal hierarchy and absent time simulation/timeline scaling.

The accurate historical implementation state is therefore **built/deployed working prototype, Phase 1 incomplete**, not merely `DESIGNED` and not a finished production interface.

The original frontend source tree/package has not been recovered from the currently accessible Drive/File Library evidence. Current availability of the old deployment has also not been revalidated. GitHub therefore contains the canonical capability definition and deployment/provenance record, but does **not** claim to contain the historical web implementation source. ## Governing purpose

Implementation choices are subordinate to the behavioural/value objective of the mechanism. BASIL should preserve and iterate the existing Visual Execution concept rather than discard it merely because the Phase 1 implementation was incomplete.

The interface should make workload pressure, temporal consequence and commitment perceptible while remaining restrained and professional. Canonical data remains authoritative; geometry, animation, colour and layout are representations of that state.

## Strategic Pressure Map

The top-level workload view is the 3×3 Importance × Urgency field:

| | Immediate | Pressing | Pending |
|---|---|---|---|
| **Critical** | 1 | 2 | 5 |
| **Important** | 3 | 4 | 7 |
| **Relevant** | 6 | 8 | 9 |

Every active task remains visible. Crowding is information: nodes compete for finite territory rather than being replaced by a count or cosmetically tidied away.

## AXIS4+1

Working execution frames:

- Strategist — direction, framing, synthesis and choice
- Analyst — evidence, investigation, modelling and evaluation
- Investor — value, allocation, leverage and return
- Engineer — building, implementation, systems and process
- Admin — filing, routine correspondence, follow-up and necessary drudgery

AXIS4+1 is an execution mindset, not a substitute for task category, objective, state or ownership.

## Gravity Channel

The Gravity Channel is the commitment/execution surface. Active tasks are represented as geometric bodies moving towards their real deadlines:

- width represents Importance
- height represents estimated execution duration
- vertical position represents time remaining to the real deadline
- colour or primary symbol may represent AXIS4+1
- new-task horizontal position contains deliberate randomness
- a completion buffer sits above the zero-time boundary
- a task becomes overdue only when its own deadline reaches Now
- overdue work may stack irregularly; BASIL should not silently optimise away the visual cost of accumulated commitments

Completion removes a task's object and permits unsupported work above it to settle into the released space.

## Forecasting and commitment

Forecast controls may simulate future workload states rather than acting as filters. The governing design distinguishes:

- **Strategic Pressure Map:** interrogation and reflection
- **Gravity Channel:** commitment and execution

Selecting a Gravity Channel task reveals sufficient task detail to act. The working commitment protocol is:

1. First selection: **Start Now** or **Skip**.
2. Each task has one skip only.
3. After the skip is used: **Start** or **Deliberate Abandonment/Delete**.
4. Abandonment removes the task from active execution while preserving source and history.

## Phase 1 implementation evidence

The 19 August 2026 engineering review of the running prototype identified these defects:

1. card collisions and overlaps
2. abrupt/static horizon changes rather than dynamic descent
3. strategy/persona controls with no observable effect
4. insufficient canvas/card geometry
5. weak Now and near-term temporal hierarchy
6. missing time simulation and timeline scaling

The same Phase 1/Milestone 1 evidence specified rigid contact/push-up stacking, dynamic horizon transitions, a strong Now floor, near-term threshold, accelerated time simulation, timeline zoom/live ticking, strategy-frame recalculation and binding to canonical BASIL task state.

These requirements demonstrate the intended implementation trajectory. They do not prove that the reviewed defects were subsequently fixed.
